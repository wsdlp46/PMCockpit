# project-iteration — 项目与迭代管家

## 目的

管理迭代型项目的项目与版本生命周期：从“初始化项目”到“版本收尾”。先建立项目骨架和基线，再让版本初始化标准化（目录骨架、资产复制、旧版标注清理），使版本收尾不留尾巴（状态校正、索引更新、总览同步）。

## 触发条件

- 用户明确说“新建项目”“初始化项目”“项目立项”→ 执行**项目初始化**
- 用户明确说“开始 V1.0.X 迭代”“新建版本”“启动下一迭代”→ 执行**版本初始化**
- 用户说“版本收尾”“结项”“归档”“收个尾”→ 执行**版本收尾**
- 用户说“_index 不对”“索引同步”“状态更新”→ 执行**索引校正**

> 不主动建议“要不要新建项目或版本”，必须由用户声明触发。

## 前置依赖

- 项目遵循四层结构，见 `01通用规则/项目工作流规范.md`
- 项目模板位于 `01通用规则/模板/项目模板/`
- 项目基线内的 `01-项目基线/项目工具/版本索引模板.md` 是每个版本 `_index.md` 的唯一模板来源
- 版本目录命名：`0X-V{MAJOR}.{MINOR}.{PATCH}`，如 `03-V1.0.2`
- 版本内目录：`01-原始需求` 至 `06-变更记录`，不单设评审纪要目录

## 流程零：项目初始化

用户明确要求新建或初始化项目时执行；通用模板目录本身不是进行中项目，不能直接在其中填写业务内容。

### 第1步：确认最小项目事实

确认项目全称、`02当前项目/` 下的目标目录名、当前项目状态，以及是否立即启动首个版本。项目全称或目录名不明确时先确认，不按简称或既有项目名称猜测。

### 第2步：创建项目骨架与项目基线

以 `01通用规则/模板/项目模板/` 为源，复制到 `02当前项目/{项目名}/`，然后替换全部 `{…}` 占位内容：

- `00-项目总览.md` 与项目 `_index.md`：只补充已确认的项目事实、角色端侧和状态；未确认项保留“待确认”
- `01-项目基线/`：保留关键决策、需求池、会议时间线与项目工具的初始化结构，不凭空写入业务规则或决策
- `01-项目基线/项目工具/版本索引模板.md`：保留在项目基线中，后续每个版本从此复制索引
- `02-迭代/_index.md`：初始为“未启动”，不预建虚假的版本目录

### 第3步：建立后续调用关系

| 业务动作 | 调用来源 | 产出位置 |
|---|---|---|
| 启动首版或下一版 | 项目基线 `项目工具/版本索引模板.md` | `02-迭代/0X-VX.X.X/_index.md` |
| 会议或二进制材料入库 | 基线会议时间线、关键决策 | `01-项目基线/` 或目标版本 `01-原始需求/` |
| 候选需求评估 | 基线 `需求池.md` | 确认后进入目标版本 |
| 已确认跨版本约束 | 基线 `关键决策.md` | 作为需求、规格、原型的前置输入 |

### 第4步：确认初始化完成

报告项目路径、已建立的基线资产和当前未确认项。只有用户明确说“开始新版本”后，才继续执行版本初始化。

## 流程一：版本初始化

用户声明开始新版本时执行。

### 第1步：确定版本号与范围

- 查 `02-迭代/` 下已有版本，确定下一个版本号；首版可提议 `01-V1.0.0`，但仍以用户确认的版本号为准
- 主版本（功能迭代）增 MAJOR，小版本（优化/补丁）增 MINOR/PATCH
- 向用户确认版本号和本版本范围

### 第2步：创建版本目录骨架和索引

```
02-迭代/0X-V1.0.X/
├── _index.md
├── 01-原始需求/
├── 02-需求文档/
├── 03-规格文档/
├── 04-原型/
├── 05-TAPD上传规划/
└── 06-变更记录/
```

`_index.md` 必须从当前项目 `01-项目基线/项目工具/版本索引模板.md` 复制创建，并替换版本号、主题、范围和日期；不再从上一版直接复制索引。

### 第3步：复制上一版资产

从上一版本完整复制（非仅差异）：

- `03-规格文档/` 的全部规格，复制到新版本 `03-规格文档/`
- `04-原型/` 的全部 HTML 和 `_scaffold/`，复制到新版本 `04-原型/`
- `02-需求文档/` 与 `05-TAPD上传规划/` 仅在本版本确有复用需要时复制，并在索引中说明

不复制 `01-原始需求` 和 `06-变更记录`，二者必须保持版本独立。

复制上一版资产时，将版本索引顶部改为“基准版本：{来源版本} ｜ 继承资产：有”，并在“资产继承”表登记来源、范围和本版本是否改动。继承资产不计作本版本已经完成的阶段。

### 第4步：清理原型旧标注

对新版本 `04-原型/` 下的源页面和交付页面，移除上一版 Pin 标注、右侧说明和已失效的版本说明；保留页面结构与公共脚手架。操作前需确保存在副本或 Git 可恢复，完成后抽查页面中不再残留旧版标注编号。

未提供可靠清理工具时，不调用不存在的脚本，也不做脆弱的批量文本替换；保留标注并在版本索引中说明，待人工或专用工具处理。旧版带标注原型保留在上一版本目录，不额外归档。

### 第5步：确认初始化完成

- 在 `_index.md` 中登记继承规格和原型的来源版本及数量，所有“阶段状态”保持“待启动”
- 向用户报告版本号、目录结构、复制的资产和实际剥离的页面数量
- 提示用户可开始需求、规格和原型工作

## 流程二：版本收尾与索引校正

用户声明版本收尾、结项或索引同步时执行。

### 第1步：校正版本索引

先按版本变更记录、已评审产出和实际交付物更新“阶段状态（本版本实际进度）”。文件数量只说明目录中有资产，不能替代本版本完成度。

仅当版本索引明确标为 `继承资产：无` 且使用标准“目录导航”表时，才可运行：

```bash
# 仅校正目录导航的文件目录状态，不更新本版本阶段完成度
bash .ai/skills/project-iteration/assets/sync-index.sh "<项目目录>/02-迭代"
```

脚本跳过继承资产或非标准索引时是正常保护行为；必须手工校正对应版本状态。

### 第2步：更新项目总览和迭代索引

- 在 `00-项目总览.md` 的版本状态表中更新本版本为“已完成”或“待评审”，如有下一版计划则补充
- 更新 `02-迭代/_index.md` 的版本清单，包括版本号、状态和范围说明

### 第3步：确认收尾完成

- 向用户报告状态校正结果，以及总览和索引的更新情况
- 主动提醒可执行 `project-retrospective-pm` 复盘，覆盖流程问题、工具链规范度和可复用沉淀

> 版本目录保留最终交付物。本流程不主动移动过程文件；过程草稿只有用户要求清理时才移入 `归档/`。

## 资产：sync-index.sh（`assets/sync-index.sh`）

脚本只扫描版本目录并更新标准“目录导航”中的**目录状态**：

- `02-需求文档/` 有 Markdown 文件，标记“需求完成(N)”
- `03-规格文档/` 有 Markdown 文件，标记“规格完成(N)”
- `04-原型/` 有 HTML 文件，标记“原型完成(N)”
- `05-TAPD上传规划/` 有 Markdown 文件，标记“TAPD完成(N)”
- 上述目录都有文件时，将顶部版本状态辅助标记为“待收尾”

脚本不更新“阶段状态（本版本实际进度）”，也不处理继承资产、非标准索引或缺少“目录导航”表格的索引。这些情况会警告后跳过，不会改写文件。

**用法**：

```bash
bash .ai/skills/project-iteration/assets/sync-index.sh "<项目目录>/02-迭代/01-V1.0.0"
bash .ai/skills/project-iteration/assets/sync-index.sh "<项目目录>/02-迭代"
```

**适用时机**：无继承资产版本的目录初始化后、文件新增或删除后，以及版本收尾的目录状态辅助校验。
