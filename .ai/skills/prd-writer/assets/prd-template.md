# PRD 框架模板

> 本文件是 prd-writer skill 输出的**唯一权威骨架**。
> 6 章结构两类共享，每章内用 `[改造类]` / `[新建类]` 标注分支写法。
> 撰写流程（怎么收集信息填进框架）见 SKILL.md，本文件只定义"骨架长什么样"。

## 使用说明

- **改造类 / 新建类的判定**：见 SKILL.md 流程一 1.1 场景路由
- **填充前先做什么**：见 SKILL.md 流程二（候选方案驱动收集）
- **省略规则**：凡标"无则省"的章节，若该次需求不涉及对应内容，整节删除，不留空壳；后续章节编号不回退（如省三章，流程图仍叫三章）
- **编号一致性**：插入/删除/移动编号项后，必须全局刷新后续编号和所有交叉引用

## 统一 6 章骨架

### 一、背景

**两类统一写法**（背景部分不区分改造/新建，都按现状/问题/目标三段）。

| 小节 | 写法 | 约束 |
|------|------|------|
| 1.1 现状 | **一段话**描述当前系统/流程/业务是怎么做的 | 一段话，不拆条目 |
| 1.2 问题 | 当前为什么不改不行，列痛点 | 痛点 ≤4 条，每条一行 |
| 1.3 目标 | 改什么 → 达到什么效果 | 一段话 |

> 背景依据写在文档头 `> 依据：#DXXX / 会议事项X`，不在正文重复展开。

### 二、范围

#### 2.1 用户角色

> **省略规则：单一用户角色则省略本节，直接进 2.2 核心功能。**（与五章跨部门配合同类条件触发）

| 分支 | 写法 |
|------|------|
| `[改造类]` | 简列：沿用现有角色体系，标注本版本受影响角色。例：`本版本沿用现有角色体系，受影响角色：A / B / C` |
| `[新建类]` | 详表，每个角色首次出现**必带一句话边界**（能做什么 + 不能做什么） |

`[新建类]` 角色表：

| 角色 | 要做什么 / 遇到什么问题 | 需要的功能 | 边界（能做什么 / 不能做什么） |
|------|---------------------|-----------|--------------------------|
| | | | |

> 角色边界规则（AGENTS.md 文档生成纪律第 4 条）：多角色共享系统时，边界不清会导致理解混乱，必须写清。

#### 2.2 核心功能

**两类共享**。一张表提炼本版本要做的核心功能清单，不展开细节（细节进四章）。

| 序号 | 核心功能 | 功能描述 |
|------|--------|--------|
| | | |

#### 2.3 不做什么

**两类共享**。明确本版本**不涉及**的范围边界，防止后续 scope 蔓延。

#### 2.4 现状与改造对照

> **`[改造类]` 专用**，`[新建类]` 省略本节。

| 环节 | 现状 | 改造后 |
|------|------|--------|
| | | |

### 三、流程图

**两类共享选择规则**。数据流方向（流程二批次 1 的判断结果）决定流程图类型：

| 判断条件 | 选什么 | Mermaid 语法 |
|---------|--------|-------------|
| 以后端技术改造为主（接口调用、数据传递、系统间交互） | **时序图** | `sequenceDiagram` |
| 以各角色业务交互为主（用户操作、运营审核、机构提交） | **角色泳道图** | `sequenceDiagram` with `participant` |
| 两种都涉及 | **同时用两张图** | — |

输出：Mermaid 图（直接嵌文档，不外链图片）+ 关键节点说明表。

````markdown
### 3.x 流程图

```mermaid
（图）
```

### 3.x 关键节点说明

| 节点 | 说明 |
|------|------|
| | |
````

### 四、功能详述

> 排序与字段两类不同，但都遵守功能描述四要素（见下）。

| 分支 | 排序 | 每条字段 | 字数约束 |
|------|------|---------|---------|
| `[改造类]` | 按 **C端 → 后台 → 接口** 排序 | 角色 / 触发 / 改什么 / 交互 | 每功能点 ≤150 字 |
| `[新建类]` | 按 **角色 × 端** 展开 | 要做什么 / 操作步骤 / 预期结果 | — |

**功能描述四要素（通用，AGENTS.md 写作风格约束）**：谁 → 什么时候（触发）→ 做什么（动作）→ 结果怎样（效果）。功能描述 ≥67 字，控制在 120 字以内。

> **分点小标题（硬约束）**：四要素每个分点**独立成段**，每个分点前用加粗短语作小标题，不得把多个分点挤在一行用斜杠或逗号串联。下面两种写法是标准范式。

`[改造类]` 写法：

````markdown
### 4.x [层面] [页面/功能]：[一句话改动说明]

**角色**：
（哪个角色使用本功能）

**触发**：
（什么操作或条件触发本功能）

**改什么**：
（本次改造的具体内容，对比现状）

**交互**：
（用户操作步骤与系统反馈）
````

`[新建类]` 写法：

````markdown
### 4.x [角色] [端] [功能名称]

**要做什么**：
（本功能解决什么问题，达成什么目的）

**操作步骤**：
（用户的具体操作路径，阿拉伯数字分点）

**预期结果**：
（操作完成后的系统状态或输出）
````

### 五、跨部门配合

> **省略规则：无跨部门事项则省略整章**（与 2.1 单一角色省同类处理）。

涉及运营 / 商务 / 法务等其他部门配合时，列配合事项和分工。

**两类统一**。固定一张表：

| 序号 | 问题 | 倾向 | 需确认方 |
|------|------|------|---------|
| | | | |

## 合规章节（改造类条件触发，非独立章）
