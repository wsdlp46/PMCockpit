# prd-writer — 产品需求文档撰写

## 目的

按统一的 6 章 PRD 框架输出需求文档。

- **框架规格**（What，6 章骨架 + 每章分支写法）：`assets/prd-template.md`
- **撰写流程**（How，怎么收集信息填进框架）：本文件流程一/二/三
- **输出纪律**（Constraint，篇幅/要素/省略原则）：本文件末节

> 本 skill 不自带模板代码块，所有章节结构和字段以 `assets/prd-template.md` 为唯一权威。

## 触发条件

- 用户说"写 PRD""写需求文档""出需求""PRD 撰写"等
- 改造现有系统的增量需求，或从零开始的新项目需求

## 前置依赖

- 项目遵循四层结构（项目 / 通用 / 迭代 / 版本内目录），见 `01通用规则/项目工作流/01-项目结构与版本治理.md`
- 版本目录结构：`02-迭代/0X-VX.X.X/`，版本内 `01-原始需求` ~ `06-变更记录`
- PRD 落位：`02-需求文档/` 下，命名 `V{版本}-{序号}-{需求名称}-PRD.md`

## 流程一：场景判断与上下文加载

接到任务后，先完成场景判断和上下文加载，不读就不许出方案。

### 1.1 场景路由（不问用户，自行判断）

| 信号 | 场景 | 填充模板 |
|------|------|---------|
| 项目有 V1.0.0 基线、用户说"改造/增加/升级"、有功能清单可对照、改动点明确 | **改造类** | `prd-template.md` 改造类模板 |
| 全新项目、从零开始、没有现有系统或功能清单 | **新建类** | `prd-template.md` 新建类模板 |

场景确定后，进入 1.2 上下文加载，再进流程二候选方案收集。

### 1.2 上下文加载（强制顺序）

候选方案的依据全部来自上下文，不读等于凭空编。按顺序加载：

1. 项目 `00-项目总览.md` + `02-迭代/_index.md`（当前文件全貌与进度）
2. `01-项目基线/关键决策.md`（候选方案的主要依据来源，引用用 `#DXXX`）
3. `01-项目基线/会议记录/` 最新文档（捕捉最新外部输入，引用用"会议事项X"）
4. 改造类额外完成 1.3 功能清单扫描
5. 涉及 B 端角色/权限/注册时，查 `03知识库/B端产品/` 模式笔记

### 1.3 功能清单扫描（仅改造类，防止"从零设计"陷阱）

> 写 PRD 前必须完成，扫描结果作为流程二批次 1 候选方案的依据来源。新建类跳过本节。

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1 | 读项目 V1.0.0 功能清单（通常在 `_source/` 或验收文档） | 全量功能列表 |
| 2 | 用户描述的每个改动点，找到对应的功能清单条目 | 标注已有/改造/新建 |
| 3 | 新建的功能确认是否真不存在（在功能清单里搜关键词） | 防止标记错误 |
| 4 | 改造的功能，明确改哪些字段/交互/逻辑 | 对照表来源 |

扫描完成后，命中的条目编号带入流程二，作为候选方案的依据标注。

## 流程二：候选方案驱动收集

> 核心原则：用户一句话丢过来后，不直接写 PRD，也不开放式追问。每个阶段先用 AskUserQuestion 给 1-3 个候选方案（最多 4 个选项），基于已加载的项目上下文推断，用户点选确认即可。信息不足时给"最可能的猜测"作为推荐项放第一位让用户否决。完全废弃开放式反问——宁可让用户否决推荐，也不让用户从零组织答案。

### 2.1 候选方案设计规则

| 规则 | 说明 |
|------|------|
| 选项数量 | 每个问题 2-4 个候选；推荐项放第一位，label 末尾加"(推荐)" |
| 依据标注 | 方案不直观、有歧义或反直觉时，在 description 里标注来源（`#DXXX` / 会议事项X / 功能清单条目号）。明显方案不标注，保持简洁 |
| 信息不足处理 | 给"最可能的猜测"作为推荐项，绝不空问。哪怕只有三成把握也先猜，让用户否决或修正 |
| 兜底入口 | 不用自己写"以上都不对"，AskUserQuestion 自动提供 Other 选项，用户可自由补充。用户选 Other 等同于"你的候选没命中，我来描述" |
| 合并提问 | 同一轮的相关问题合并到一次 AskUserQuestion 调用（最多 4 问），减少打断。一次调用里的问题彼此独立、不互相依赖 |
| 选项 label | 控制在 1-5 词，长说明放 description，不放 label |

### 2.2 改造类候选批次

**先做 1.3 功能清单扫描**，拿到命中条目后再出候选，否则候选无依据。

**批次 1 — 定位改动范围**（一次调用 3-4 问）：

| 问题 | 候选来源 | 不直观时标注 |
|------|---------|-------------|
| 改动涉及哪些层面 | 扫描命中的功能清单条目，按 C端/后台/接口分组给候选 | 命中条目编号 |
| 改动类型 | 扩字段 / 改流程 / 新增功能 / 改交互（基于用户描述推断） | 用户描述有歧义时标注推断依据 |
| 数据流方向 | 端到后台 / 后台到端 / 系统间双向 / 无后端改动 | 改动层面不直观时标注 |
| 是否跨部门配合 | 默认"否"放推荐；会议记录提到法务/商务/运营介入则候选"是" | 会议事项编号 |

> **数据流方向同时决定流程图类型**（填三章流程图时参考）：端↔后台交互多选时序图，角色交互多选泳道图。完整规则见 `prd-template.md` 第三章。

**批次 2 — 确认边界细节**（可选，仅当批次 1 暴露需要展开的点）：

| 问题 | 候选来源 |
|------|---------|
| 边界数值/字段规则 | 基于关键决策和会议记录给常见值候选（如有效期给 7/30/90 天三选一） |
| 异常处理分支 | 基于改动类型给候选（失败重试 / 降级返回 / 前置拦截） |
| 流程图类型（可选） | 时序图 / 泳道图 / 双图（基于数据流方向推断） |

### 2.3 新建类候选批次

**批次 1 — 角色与场景**（一次调用 2-3 问）：

| 问题 | 候选来源 | 不直观时标注 |
|------|---------|-------------|
| 目标用户角色 | 基于背景给 2-3 个最可能角色，每个 description 带一句话边界（能做什么/不能做什么）。单一角色则直接省略 2.1 | 角色边界不清时标注 |
| 核心要解决的事 | 基于上下文给 2-3 套痛点假设 | — |
| 业务约束 | 行业监管/合规/数据来源等，基于项目领域给候选 | 监管要求来源 |

**批次 2 — 功能与流程**（一次调用 3-4 问）：

| 问题 | 候选来源 | 不直观时标注 |
|------|---------|-------------|
| 涉及哪些端 | 基于角色和场景给端侧组合候选（如 PC后台 / 小程序+H5 / 多端） | — |
| 核心功能组合 | 提炼 2-3 套功能集方案（最小集 / 标准集 / 完整集），让用户圈范围 | 取舍依据 |
| 流程图类型 | 时序图 / 角色泳道图 / 两者同用（基于是否跨系统） | — |
| 是否跨部门 | 同改造类 | — |

**批次 3 — 边界**（可选）：

| 问题 | 候选来源 |
|------|---------|
| 约束/数值/边界情况 | 基于行业常识和项目领域给候选 |

### 2.4 收尾规则（追加 / 提前结束 / 输出时机 / 反例）

**何时追加候选轮**（仍以候选形式呈现，不开放式追问）：

- 用户点选暴露新分歧（如选了"新增功能"但功能名有歧义）→ 出候选让用户消歧
- 某方案需要展开细节（如边界数值有多种算法）→ 出算法候选让用户选
- 用户在 notes 里提出新约束需要确认范围 → 把约束转成候选让用户确认

**提前结束**：

- 用户在任一轮 notes 里一次性覆盖了后续问题的核心答案 → 跳到输出，不重复追问
- 用户说"就这些""差不多""可以了" → 跳到输出
- 不因为"还有候选没出"而强行追问已经明显的信息

**输出时机**：

所有候选批次完成（或用户提前覆盖）后，一次性输出完整 PRD 到 `02-需求文档/` 下，按 `V{版本}-{序号}-{需求名称}-PRD.md` 命名。边问边写、分段输出、让用户边回答边审阅中间稿都不对——等全部收集完再输出。

**反例：什么算违规**

| 违规动作 | 问题 | 正确做法 |
|---------|------|---------|
| 开放式问"这个需求涉及哪些功能？" | 把组织答案的活推给用户 | 先扫描功能清单，把命中条目作为候选选项给出 |
| 开放式问"用户角色是谁？" | 用户得从零描述 | 基于背景给 2-3 个最可能角色候选 |
| 问完一轮等用户回，再想下一轮 | 节奏拖沓 | 相关问题合并到一次调用，最多 4 问 |
| 候选项不带依据，用户难验证 | 方案可信度低 | 不直观的方案在 description 标注 `#DXXX` 或会议事项 |

## 流程三：输出 PRD

所有候选批次完成（或用户提前覆盖）后，一次性输出完整 PRD。

### 3.1 套模板填充

1. 读取 `assets/prd-template.md`，按场景（改造类/新建类）选择对应的可填充模板
2. 按流程二收集到的信息，逐章填充
3. 应用省略规则（单一角色省 2.1；无跨部门省五章；改造类无数据输出不加合规）
4. 删除不适用的章节后，**刷新后续编号**，确保 1-6 章连续

### 3.2 文件命名与落位

- 命名：`V{版本}-{序号}-{需求名称}-PRD.md`，如 `V2-1-用户授权信息获取改造-PRD.md`
- 落位：`02-需求文档/`
- 文档头注明依据（`#DXXX` / 会议事项X）、编号、状态（初稿待评审）

### 3.3 关于小需求

> 本 skill 当前只提供完整版 6 章框架（`prd-template.md`）。**小需求（轻量需求文档）模板待补**——后续按需新增 `assets/quick-template.md`，届时在 1.1 场景路由里追加"小需求"分支即可。

## 流程四：交付前自审

PRD 写完不等于交付完。输出文件后逐项过一遍自审清单，发现问题立即修，修完才算完成：

| # | 检查项 | 判定标准 |
|---|--------|---------|
| 1 | 章节完整 | 六章齐全（或按省略规则删章后编号连续），无空壳章节 |
| 2 | 业务目标 | 1.3 目标能用一句话说清，与 1.2 问题对应 |
| 3 | 角色覆盖 | 2.1 每个角色在 2.2 核心功能中都有对应功能，无角色悬空 |
| 4 | 功能边界 | 2.3"不做什么"非空，边界有依据（`#DXXX`/会议事项），不是凑数 |
| 5 | 数据口径 | 字段定义、统计规则、单位/时区等口径已写明；与后端未对齐的进六章待确认 |
| 6 | 权限逻辑 | 每个功能点写明哪些角色可用；多角色共享的功能写明数据范围差异 |
| 7 | 异常流程 | 关键流程的异常分支已列出（失败/降级/拦截），不允许只有正常路径 |
| 8 | 兼容性（改造类） | 旧功能兼容性已评估；4.x 各功能点标注功能清单命中条目号 |

> PRD 评审后的修改结论记入版本 `06-变更记录/`。修改 PRD 涉及已画原型时，触发原型、规格、需求三方联动（见《文档与页面资产规范》“页面联动与确认门”）。

## 输出纪律

### 篇幅控制

- 背景 ≤300 字，现状一段话
- 单个功能点 ≤150 字
- 表格优先于段落

### 功能描述四要素

谁（角色）→ 什么时候（触发条件）→ 做什么（动作）→ 结果怎样（效果）。省略"必要性分析"等附加描述，除非用户要求。功能描述 ≥67 字，控制在 120 字以内，阿拉伯数字分点。

> **分点小标题（硬约束）**：四要素的每个分点（角色 / 触发 / 改什么 / 交互，或 要做什么 / 操作步骤 / 预期结果）必须**独立成段**，每个分点前用加粗短语作小标题，不得把多个分点挤在一行用斜杠或逗号串联。写法见 `prd-template.md` 第四章。

### 流程图

Mermaid 格式，直接嵌在文档中，不外链图片。选择规则见 `prd-template.md` 第三章。

### 省略原则

- 没有跨部门配合的省第五章（整章删除）
- 单一用户角色省 2.1（整节删除）
- 改造类无数据输出不加合规章节
- 省略后刷新后续编号，不留空壳

### 扫描联动（改造类）

改造类 PRD 必须先完成 1.3 功能清单扫描再动笔；扫描结果（命中条目编号）作为 2.2 批次 1 候选方案的依据来源。
