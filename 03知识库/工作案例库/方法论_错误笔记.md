# 错误笔记

> 从过往案例中记录的"坑"，以及如何避免。真正的进步来自反思。

---

## 错误 1：核心 PRD 膨胀到无法维护

### 来源案例
停车 V3.0 PRD（5.8MB，单文件）→ 后续版本 PRD 越来越重

### 现象
- V3.0 主 PRD 试图覆盖路侧/商业停车场/诱导/共享停车 4 条业务线
- 单文件 5.8MB，打开慢，更新时容易遗漏
- 城市定制化内容也试图塞进主 PRD

### 根因
- 过早追求"一个大而全的文档"
- 没有区分"平台级 PRD"和"模块级 PRD"
- 多业务线共用一本 PRD 的惯性

### 如何避免
- **按业务线拆分**：路侧 PRD、商业停车场 PRD、诱导 PRD、共享停车 PRD 各自独立
- **主 PRD 只写共同部分**：平台基础能力 + 各业务线索引
- **阈值**：PRD 超过 3MB 或 50 页就该拆分

### 当前状态
已改进。双碳平台 PRD 按模块组织（9 个二级模块各自有独立的设计规格文档），主 PRD 控制在精简版。

## 错误 2：功能边界模糊导致范围蔓延

### 来源案例
- 双碳平台早期：招标文件提到碳普惠/碳足迹/绿色金融等 8 个子系统，但 Excel 清单没有对应功能
- 停车 V3.0 早期版：试图覆盖"所有停车相关功能"

### 现象
- 需求文档写了超出合同范围的功能
- 评审时发现和实际交付能力不匹配
- 砍功能时各方意见不一致

### 根因
- 没有在 PRD 开头就明确"本次不做"的清单
- 招标文件文字描述和功能清单之间的差异没有第一时间识别
- 缺乏一个权威的"功能边界锚点"（如合同 Excel 清单）

### 如何避免
- **PRD 必须有 Out of Scope 章节**：列出本次不做的功能，越具体越好
- **招投标项目以 Excel 清单为准**：招标文字是"理想"，Excel 功能清单才是"合同"
- **每次评审第一问**："这个功能在清单里吗？"

### 当前状态
已改进。双碳平台 PRD 开头就明确了"平台本身不直接承载双碳业务"，并以 Excel 清单的 226 项功能为唯一边界。

## 错误 3：设计方案没有模板化

### 来源案例
停车早期设计方案格式不统一（2019-2020 年初），后期才出现 `设计方案模板.docx`

### 现象
- 152 份方案文档格式各异
- 有些方案有报价，有些没有
- 同样的定制化需求（月卡、优惠券），不同城市的方案结构不同

### 根因
- 方案撰写初期没有模板
- 不同客户的需求催生不同格式，没有收敛
- 人走了方案格式就走了（隐性知识）

### 如何避免
- **第一个项目结束后就做模板**：不要等到做了 10 个方案再总结
- **模板包含必选章节**：背景→痛点→方案→报价→排期，缺一不可
- **定期审计格式一致性**：每季度抽查 5 份方案，检查模板遵从度

### 当前状态
已有 `01通用规则/` 下的通用模板和检查清单，但方案模板仍需检查是否与当前工作方式匹配。

## 错误 4：角色定义滞后于功能设计

### 来源案例
双碳平台：功能按模块划分完成后，才在评审中讨论出四端五角色。停车 V2.x：早期的角色只有"用户"和"管理员"，随着业务复杂才逐步分化。

### 现象
- 功能写完了，但不知道谁能用、谁能看
- 权限设计变成"后期补丁"，而非前置于功能设计
- 同一个功能不同角色看到的内容不一致，但 PRD 没区分

### 根因
- 功能清单驱动的方式，天然倾向"先列功能再分角色"
- 招标文件通常不定义角色，只列功能
- 角色划分需要业务理解，而功能清单是"中性"的

### 如何避免
- **先画角色地图再写功能清单**：在功能展开之前，先定义谁用这个平台、怎么用
- **功能描述必须带角色**："[角色] 可以 [操作] [对象]"的格式
- **每个功能必须标注所属端**：管理运营端/数据工程端/服务调用端/资产消费端

### 当前状态
已改进。双碳平台 PRD 中，角色定义和功能分配前置到了第二章（信息架构），每个场景描述都带了角色。

## 错误 5：方法论笔记没有即时记录

### 来源案例
本次建库过程中发现：停车 V3.0 的很多决策逻辑已经遗失，只能从文件名和 MEMORY.md 中断断续续地推测。

### 现象
- 知道"当时做了什么"，但说不清"为什么这样做"
- 关键决策的上下文依赖个人记忆
- 项目交接时只能交出文档，交不出决策逻辑

### 根因
- 只在项目结束或换工作时才写总结
- 日常工作中没有记录"关键决策时刻"的习惯
- 决策分散在聊天记录、会议纪要、邮件中

### 如何避免
- **每个里程碑花 30 分钟记录关键决策**：按"决策→备选→理由→影响"四栏表格式
- **遇到坑即时记**：不需要等完美格式，一句话也行
- **决策记录贴在 PRD 或 MEMORY.md 里**：不单独存放，确保在上下文中

### 当前状态
需要养成习惯。MEMORY.md 中已有部分决策记录（双碳平台、城市数据空间），但停车时期的决策大多遗失。

## 错误 6：生成摘要/汇报时遗漏保留项的业务说明

### 来源案例
Token 算力服务平台 MVP 规划汇报：New API 的邀请/联盟系统在需求文档中明确保留（"人人可推荐+代理可分润"两层漏斗），但生成汇报时完全未提及。

### 现象
- 源文档中标记为"保留"的原有功能，在摘要/汇报中被无声忽略
- 读者看到汇报后，不知道这些功能是否还存在
- 保留项的业务意义（如"形成两层漏斗"）丢失

### 根因
- 生成摘要时只关注"新增"功能，忽略"保留"功能
- 保留项不在核心功能章节（通常在"原功能处理"章节），容易被漏
- 没有检查"保留项是否也需要在汇报中说明"

### 如何避免
- **生成摘要时检查保留项**：逐条过"原功能处理"章节，保留项也要在汇报中出现
- **保留项要说明业务意义**：不只是"保留"，还要说"为什么保留、和新增功能的关系"
- **跨章节关联**：保留项的业务意义如果和新增功能形成组合拳，要显式点明

### 当前状态
已作为"文档生成纪律"第 1 条（完整性校验）和第 5 条（流程闭环校验）的补充案例。

## 错误 7：竞品调研未确认客户场景就开写，整篇返工

### 来源案例
算力星图「企业 AI 算力套餐收费模式调研」（2026-06-27，本会话）

### 现象
- 用户要求调研企业套餐收费模式，AI 基于"政企/教育"的客户假设直接写了完整调研报告（V1.2）
- 用户中途纠正："主要场景是开发团队和漫剧团队"——假设错误，整篇报告重写为 V2.x
- 同一场调研还连续踩了多个坑：漏查智谱企业席位套餐导致"国内零先例"论断被证伪、把模型厂商自带的缓存命中差价当成平台差异化卖点、ChatGPT/Claude 价格只写入门档被用户质疑

### 根因
- 调研开始前没有强制确认"客户场景假设"这一最关键输入
- 竞品分层选取时没有做覆盖度校验，漏掉国内代表（腾讯、智谱企业套餐）
- 下绝对化结论前没有主动搜反例
- 没有区分"平台差异化"和"厂商自带能力"

### 如何避免
- **调研前置确认四项**：调研主题、客户场景假设、报告用途、决策定位，未确认不动手
- **竞品分层后做覆盖度校验**：逐层问"这层还有谁"，用户点名的竞品必须纳入
- **绝对化结论前搜反例**：准备写"X 没有 Y"时，先搜一次反例，搜到则收窄论断
- **差异化卖点要判定**：声称差异化前先问"这是我方独有还是对方也有"

### 当前状态
已技能化为 `competitor-analysis-pm` skill（六阶段流程+节点闸门），相关规则同步写入工作区 AGENTS.md 硬约束第 10-13 条。
