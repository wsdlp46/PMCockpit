# 模式笔记

> 从案例中提炼的跨项目通用模式。回答"什么时候该用什么方法"。

---

## 模式 1：B端平台的四端多角色架构

### 来源案例
- 双碳平台：四端五角色（管理运营端/数据工程端/服务调用端/资产消费端 + 数据提供方跨端）
- 智慧停车：管理后台/用户端/运营端/交警端 + 设备厂商/银行
- 数据空间：平台运营方/空间运营方/参与方/监管方

### 模式描述

当 B 端平台需要服务多种不同角色，且角色的操作界面和功能差异很大时，不要试图做一个"大而全"的后台。应该：

1. **按端分离**：不同角色看到完全不同的界面（而非同一个后台的不同菜单）
2. **核心区分维度**："人看界面" vs "机器调 API" — 这是最根本的分界线
3. **跨端角色**：有些角色需要跨端访问（如数据提供方既有非技术提交又有技术对接），允许但在两端给出不同入口

### 适用场景
- B 端平台，需要服务 3+ 种不同角色
- 角色的操作方式差异大（管理配置 vs 数据加工 vs API 调用 vs 浏览查看）
- 有对外服务的 API/开放平台需求

### 不适用场景
- 纯对内工具（只有 1-2 种内部角色）
- C 端产品（角色单一）

## 模式 2：标品 + 定制分层

### 来源案例
- 智慧停车 V3.0：标品（缴费/泊位/月卡）+ 城市定制（支付渠道/银行分账/硬件对接/本地活动）
- 数据空间：城市数据空间（通用标品）+ 水投行业数据空间（行业定制）

### 模式描述

当产品需要服务多个客户但每个客户有差异化需求时：

1. **标品层**：收敛到最小公倍数，只放"所有客户都需要"的功能
2. **定制层**：按客户/行业隔离，每客户独立版本号
3. **文档分层**：主 PRD + 客户定制化需求确认单（轻量），不是每个客户写一本 PRD
4. **定期收敛**：定制化功能中高频出现的，下沉到标品层

### 适用场景
- 多客户交付的 ToB/ToG 产品
- 每个客户在支付、对接、业务规则上有差异
- 需要同时维护多个客户版本

### 不适用场景
- SaaS 标准化产品（不做定制）
- 单客户项目

## 模式 3：招投标驱动需求分析

### 来源案例
- 双碳平台：从招标文件 + Excel 功能清单解析出 PRD
- 停车多个城市项目：从标书技术得分项倒推功能优先级

### 模式描述

当需求源头不是用户访谈而是招标文件时：

1. **第一遍：找矛盾** — 招标文件文字描述 vs Excel 功能清单，找出范围不一致的地方
2. **第二遍：定定位** — 基于功能清单反向推导平台定位（能做什么、不能做什么）
3. **第三遍：定边界** — 严格以 Excel 清单为准，清单外的功能砍掉
4. **第四遍：做展开** — 每个功能点写 120 字描述，形成 PRD
5. **关键原则**：标书写的是"理想"，Excel 清单才是"合同"

### 适用场景
- 政府采购/招投标项目
- 需求来自标书而非用户调研
- 功能范围由合同约定

### 不适用场景
- 自研产品（需求来自用户/市场）
- 敏捷迭代项目

## 模式 4：数据全链路价值链设计

### 来源案例
- 双碳平台：采集→治理→存储→标注→资产化→服务输出
- 数据资产管理：登记→确权→评估→定价→收益分配→流通→处置

### 模式描述

数据类平台的核心设计方法是先画出"数据价值链"，再按链路上的每个节点展开功能模块：

1. **画链路**：数据从哪来，经过哪些环节，最终到哪去
2. **定节点**：每个环节需要什么能力
3. **配角色**：哪个角色负责哪个环节
4. **补运营**：在数据链路的末端加上运营能力（上架/定价/统计/报表）

### 适用场景
- 数据平台/数据中台类产品
- 数据资产管理系统
- 数据治理/数据运营平台

### 不适用场景
- 业务应用系统
- 纯工具型产品

## 模式 5：渐进式文档工作流

### 来源案例
- 个人偏好：PRD → 架构图 → 脑图功能清单 → 原型图（四步流程）
- 案例库的建立：索引 → 案例 → 方法论（三层递进）

### 模式描述

不要试图一步到位写出完美文档。渐进式推进：

1. **PRD**：先定范围和边界（做什么、不做什么）
2. **架构图**：再定结构和关系（谁和谁怎么连）
3. **功能清单**：展开到可数颗粒度（每个功能 120 字）
4. **原型图**：最后才画界面（有前三步打底，原型不会跑偏）

每步有明确的产出物和评审标准，上一步没确认不进入下一步。

### 适用场景
- 所有 B 端产品的需求到设计流程
- 需要多方对齐的复杂项目

### 不适用场景
- 快速原型验证项目
- UI 驱动的 C 端产品

## 模式 6：B端角色身份赋予（而非独立注册）

### 来源案例
- Token 算力服务平台：代理商不需要独立注册入口，而是统一注册后由平台运营方在后台"赋予"代理身份
- 双碳平台：数据提供方角色也是在已有账号基础上赋予，不单独注册

### 模式描述

当 B 端平台存在"特殊角色"（如代理商、认证企业、审核员）时，不要给每个角色设计独立的注册入口。应该：

1. **统一注册入口**：所有用户通过同一个注册流程创建账号
2. **后台赋予身份**：特殊角色（代理/企业/审核员）由运营方在管理后台指定，而非用户自己选择
3. **身份生效方式**：被指定后，用户侧边栏自动增加该角色的专属功能模块，与原有功能共存
4. **非独立后台**：角色功能嵌入同一后台，通过菜单分组区分，不搭建独立端

### 适用场景
- B 端 SaaS 平台，角色之间有层级或管控关系
- 角色身份需要审核或授权，不适合用户自主选择
- 角色数量可能扩展（先做一级代理，后续加二级）

### 不适用场景
- 角色之间完全独立，无管控关系（如 C 端用户/商家分离）
- 角色注册需要提交完全不同的信息（如企业要营业执照、个人不要）

## 模式 7：权限/配额的层级继承

### 来源案例
- Token 算力服务平台：企业 IP 白名单采用"企业全局默认→部门默认→个人覆盖"三层继承
- 智慧停车：费率规则也有"城市默认→区域覆盖→车场覆盖"的层级

### 模式描述

当企业/组织内的权限或配额需要分层管理时，采用"继承+覆盖"模式：

1. **层级定义**：按组织层级从上到下定义默认规则（如全局→部门→个人）
2. **默认继承**：下级自动继承上级规则，显示"继承自 XX 部门"和继承的内容，不可编辑
3. **自定义覆盖**：切换到"自定义"态后，继承的值预填入编辑区，用户可修改
4. **恢复继承**：自定义态可随时切回，清空个人规则，重新跟随上级
5. **标识区分**：列表中标注"已自定义"标记，帮管理员识别脱离继承的个体

### 关键交互设计
- 继承态：显示来源+内容，灰化不可编辑
- 自定义态：值预填，可增删改
- 切换时有确认提示："切换为自定义后将不再跟随部门规则变更"

### 适用场景
- 企业 SaaS 中的配额、权限、白名单等分层配置
- 组织结构层级分明，上级规则应自动下放
- 个别成员需要特殊配置但不影响整体

### 不适用场景
- 规则无层级关系（如独立用户的独立配置）
- 所有个体配置都不同，继承没有意义

## 模式 8：统一注册+后置分流

### 来源案例
- Token 算力服务平台：注册页不做角色选择，注册后引导页分"个人开发者"和"企业管理团队"
- 主流 B 端 SaaS（飞书/钉钉）：注册后引导选择"加入团队"或"创建团队"

### 模式描述

当 B 端平台需要区分多种用户身份，但不想在注册环节增加决策负担时：

1. **注册页统一**：只做最基础的注册（手机号/邮箱+密码+验证码），不出现角色选择
2. **注册后引导**：注册成功进入引导页，展示 2-3 个路径卡片，用户点击选择
3. **审核期间可用**：选了需要审核的路径（如企业），审核期间个人基础功能正常使用
4. **路径可切换**：选择后仍可后续升级/切换（个人可升级企业）

### 为什么不在注册时分流
- 注册页加选择会增加认知负担，降低转化率
- 用户此时对平台还不了解，可能选错
- 审核需要时间，审核期间不应阻断用户使用

### 适用场景
- B 端平台，有 2+ 种用户身份
- 某些身份需要审核才能激活
- 希望降低注册门槛、提高转化

### 不适用场景
- C 端产品（通常只有一种身份）
- 角色注册信息差异极大（企业要营业执照，个人不要）——此时需要注册分流
