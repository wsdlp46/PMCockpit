## 一、文章核心观点

Spec（Spec-Driven Development）不是"更详细的 PRD"，而是介于 PRD 和工程实现之间的**可执行上下文**，把业务需求翻译成研发和 AI Coding 工具都能使用的工程上下文。

传统 PRD 停在业务描述层（为什么做、给谁用、做什么功能）；研发拿到后仍要做"二次翻译"——把业务语言翻译成接口、数据、状态、异常、测试边界。AI Coding 介入后，AI Agent 最怕上下文模糊，模糊上下文会导致 Demo 能跑但不可上线。

### Spec 相对 PRD 需要补充的维度

| 维度 | 传统 PRD 常见写法 | Spec 需要补充 |
|------|---------------|-------------|
| 业务目标 | 说明为什么做 | 明确成功标准和不做什么 |
| 用户流程 | 描述主流程 | 补状态、权限、异常和兜底 |
| 功能范围 | 列功能点 | 拆成可开发任务 |
| 数据 | 说需要哪些信息 | 明确字段、来源、读写规则 |
| 接口 | 可能只写对接系统 | 明确入参、出参、错误码 |
| AI 能力 | 写"智能生成" | 明确输入、输出、置信度、人工确认 |
| 验收 | 写功能可用 | 给测试样例和通过标准 |

### AI 时代产品研发对齐的五个变化

1. **产品经理要定义 AI 的能力边界**——AI 能做什么、不能做什么、哪些必须引用来源、哪些必须人工确认、低置信度怎么兜底
2. **产品经理要提供样例，而不只是描述**——输入样例、输出样例、正确样例、错误样例、Badcase、验收样例
3. **研发拆的不只是功能，还有 AI 链路**——Prompt、RAG 知识库、Agent 工作流、工具调用、权限控制、置信度判断、人工确认节点、日志审计、Badcase 回流
4. **对齐方式从一次性交接变成持续校准**——Spec 初版 → 快速 Demo → 业务验收 → 发现 Badcase → 补 Spec/Rules/测试样例 → 再迭代
5. **验收从"功能可用"变成"结果可控"**——回答是否有依据、召回是否命中、生成是否幻觉、置信度低是否兜底、是否越权调用、Token 成本是否可控、Badcase 是否能回流

### Spec 示例结构（以"会议录音生成需求分析文档"为例）

```
功能：会议录音生成需求分析文档
输入：audio_file / customer_id / project_type / uploader_user_id
处理流程：
  1. ASR 转文字
  2. 抽取客户背景、痛点、功能需求、预算、时间、约束
  3. 检索相似历史项目
  4. 相似度高于阈值 → 输出可复用方案建议
  5. 相似度不足 → 生成新需求分析初稿
  6. 所有结果进人工确认节点，不自动进开发池
AI 能力边界：
  - 只能生成初稿
  - 不允许自动确认客户需求
  - 不允许自动承诺交付周期
  - 不允许自动生成报价
异常处理：
  - ASR 失败：提示重新上传
  - 知识库无匹配：走新需求分析
  - 置信度低：标记"需人工确认"
验收标准：
  - 30 分钟以内录音 5 分钟内生成初稿
  - 文档必须包含来源引用
  - 进入下一流程前必须有人确认
```

## 二、与本工作区现有规格体系的对照

| 维度 | 文章的 Spec | 本工作区「原型设计规格」 |
|------|-----------|-------------------|
| 定位 | PRD 与工程实现之间的可执行上下文 | PRD 与原型开发之间的页面级设计依据 |
| 服务对象 | 研发 + AI Coding Agent | 原型开发 + 评审 |
| 终止线 | 到"可上线"边界（接口契约、AI 链路、验收样例） | 到"可画原型"边界（页面结构、字段、状态、交互） |
| 关系 | 本工作区规格是文章 Spec 的**前置一层** | 后续研发侧 Spec（接口契约、AI 链路）由 solution-designer agent 承接 |

### 已借鉴落地（2026-07-03 纳入 proto-spec-generator）

1. **异常与兜底章节**：在规格模板「末、交互规则」前新增「次末、异常与兜底」，结构化承载空数据、提交失败、接口超时、权限不足、加载异常、并发冲突等场景。简单只读页面也必须显式声明"无特殊异常兜底"，不得跳过。
2. **字段配置表加示例值列**：字段表从"序号/字段/类型/必填/说明"升级为"序号/字段/类型/必填/示例值/说明"。枚举/格式/金额/日期类字段必填示例值，示例值是样例不是定义。

### 待借鉴（遇到 AI 项目时启用，不全局铺开）

3. **AI 能力边界条件章节**：当页面承载 AI 类功能（智能生成/匹配/推荐/核算）时，强制输出：输入是什么 / 输出是什么 / 哪些可自动 / 哪些必须人工确认 / 低置信度兜底。非 AI 页面不触发，避免模板臃肿。
4. **Badcase 回流闭环**：评审中发现的字段/状态/异常兜底问题，回流补进对应规格文档（由 project-retrospective-pm 的五级联动承接，不改 proto-spec-generator）。

### 明确不借鉴（避免越界）

- **接口契约（入参/出参/错误码）**：后端详细设计或 Swagger 职责，由 solution-designer agent 承接，不塞进原型规格
- **AI 链路拆解（Prompt/RAG/Agent 工作流/Token 成本）**：纯研发侧，不在 PM 规格范围
- **"上下文设计师"全套角色重定义**：方法论层面，不落地到具体 skill

## 三、使用指引

- **当前项目（政务 B 端、算力、双碳）**：用已落地的第 1、2 点即可，规格照常出
- **遇到含 AI 能力的项目时**：先读本文件第二部分"待借鉴"第 3 点，在 proto-spec-generator 中加条件章节；同时参考文章的 Spec 示例结构，把 AI 能力边界、异常处理、验收标准三块补进规格
- **AI 链路详细拆解**：转给 solution-designer agent，不在原型规格层做
